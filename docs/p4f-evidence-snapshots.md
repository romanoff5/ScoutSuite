# P4-F — anonymized evidence snapshots (version 1)

## Security contract

P4-F exports **finding observations**, not a raw AWS API capture. This is intentional: Scout RESULTS can contain DNS names, user data, policy documents, identifiers, and secret-bearing configuration values. Applying a generic recursive regex replacement to AWS data would not reliably remove all secrets and could change rule semantics.

The portable snapshot is built by an **explicit allowlist** of: validated service/rule keys, enum-only evidence states, integer counters, HMAC-tokenized collection issue codes, local rule-definition SHA-256, and keyed HMAC tokens of observed resource paths. It does not serialize raw AWS account IDs, ARNs, usernames, DNS names, AWS API response bodies, IAM policies, customer resource attributes, error messages or the HMAC key.

The key is a locally stored **32-byte random secret**, created with restrictive permissions. The snapshot includes only a non-reversible key identifier and an HMAC-SHA-256 authenticity tag. Using the **same key** across exports provides stable pseudonym tokens for comparing snapshots; using different keys deliberately prevents linking identities. Never commit the key or original RESULTS files.

The bundle supports:
- `export`: allowlist projection, canonical JSON and HMAC signing.
- `replay`: integrity verification, evidence-counter and token reconciliation, and current on-disk JSON **rule-definition drift** detection; **zero AWS API calls**.
- `diff`: new/resolved *observed* hashed finding identities using the same key, including rule version and evidence completeness changes.

This is **observation replay**, NOT reexecution of current rule predicates over captured AWS source data. If a rule definition changed, replay reports `rule_definition_drift`; a finding cannot be automatically re-evaluated without safe semantic inputs. The integrity tag attests to a locally exported snapshot only if the identity key remains secret; it is not an AWS audit-signing service.

## Commands

From the repository root:

```bash
python tools/p4f_evidence.py init-key --key-file ./.p4f.snapshot-key
python tools/p4f_evidence.py export --report ./scoutsuite-report/scoutsuite-results/RESULTS.json --key-file ./.p4f.snapshot-key --output ./assessment.p4f.snapshot.json
python tools/p4f_evidence.py replay --snapshot ./assessment.p4f.snapshot.json --key-file ./.p4f.snapshot-key
python tools/p4f_evidence.py diff --before ./before.p4f.snapshot.json --after ./after.p4f.snapshot.json --key-file ./.p4f.snapshot-key
```

Use the **actual local RESULTS path** generated by Scout Suite; JSON and exact `scoutsuite_results = {...}` JS assignment formats are supported. Outputs are created exclusively (never overwritten) and with private file permissions. Source file paths and raw errors are not printed by the CLI.

Exit statuses: `0` complete authenticated observations / successful export / successful diff; `2` authenticated but incomplete observations or unavailable/changed local rule definitions; `3` malformed data, permission violations or failed integrity checks.

## Provenance and stable evidence model

- `format/schema_version`: exact `scoutsuite-evidence-snapshot` v1 contract.
- `source_results_schema_version`: legacy version compatibility marker (0 or 1).
- `scanner_version`: public ScoutSuite build version.
- `key_id`: HMAC-derived key ID; no raw customer account identifier.
- `rule_definition_sha256`: local JSON rule-definition hash, or `null` if unavailable.
- `flagged_identity_tokens/unknown_identity_tokens`: domain-separated HMACs scoped by (account, service, rule, path).
- `evidence_counts`: per-rule observed secure/insecure/unknown/not_applicable counts; absent policy evidence is `unavailable`, never PASS.
- `collection`: issue scope/status plus HMAC of reason (never raw SDK errors).
- `integrity`: canonical body digest and key-dependent HMAC authentication.
- `verification_scope`: explicitly `observed_finding_evidence_only`; effective authorization and compliance are never claimed verified.

Re-exporting the same report and key produces byte-for-byte equivalent canonical bodies and signatures (assuming unchanged scanner version and rule files), independent of dict and item insertion order.

## Limitations and next evolution

1. This first version cannot recreate a network state, call AWS or recompute predicates from raw data. Future P4-F stages can introduce **service-specific allowlisted semantic facts** and test them through the live rule engine; never expose generic unsanitized API payloads.
2. No verified end-to-end delivery from AWS, and no claim about completeness of an AWS scan. Any collection issues remain `incomplete` and do not imply a clean account.
3. Rule-definition drift is explicit. A report from an older version cannot be silently reinterpreted with a modified rule.
4. HMAC token stability requires the original key. Protect it as an assessment secret; if lost, a historical snapshot remains inspectable but cannot be authenticated or linked to later snapshots.
5. Do not treat a `verified_observations` replay as evidence of secure AWS configuration. It verifies the artifact and its recorded counters only.
6. Existing RESULTS files still contain sensitive source inventory; only share the P4-F projection after independent privacy review when required by contract.

For **rule-logic regression**, continue to run source-to-rule fixtures and metamorphic tests on wholly synthetic AWS payloads. P4-F adds a private-safe reproducibility and drift envelope around those outcomes; it does not replace the fixture suite.

Only names present in installed AWS service metadata are emitted. Unknown/custom rule names are HMAC-pseudonymized and flagged `definition_unavailable`, not exported verbatim. This prevents user-created naming conventions from silently leaking identifiers.
